更新：2026-09-23。本文件把 [04 角色矩阵](04_角色功能与范围矩阵.md)、[05 功能 UI](05_UI与功能颗粒度规格.md)、[06 表关系](06_数据库字典与实体关系.md) 连成可开发切片。接口路径为建议契约；已有工程有等价实现时更新映射，不平行维护两套接口。

第一步已验证部分、实际接口与状态映射见 [08 实施交付记录](08_第一步实施交付记录.md) 和 [后端接口说明](../../apps/api/README.md)。当前采用 DRF 分页、version 字段及单人画像确认接口；这是 F01/F02/F04/F06/F07 的部分实现，不代表 D01 全部扩展或整个 P0 已完成。后续客户端沿用实际契约，不另建一套状态。

## 1. 技术执行约定

继续使用 React＋TypeScript＋Tailwind＋shadcn/ui＋Semi；候选人／后续 HR 移动为 Flutter；Django／DRF 业务后端；PostgreSQL 真实数据。先用 Django 单体模块完成闭环，不建立微服务、通用审批引擎或任意插件执行器。解析／模型／消息到对应切片需要异步时再接队列和 Redis。

浏览器优先同源会话＋CSRF；飞书身份绑定同一 User／Membership。Flutter 使用后端支持的可撤销登录凭证与同一权限校验，机密不打包进客户端；候选人本人认证与内部员工身份区分。具体认证库、依赖及版本由实现任务查官方兼容范围并锁定，文档不以未核验的安装状态代替实测。

开发任务在独立工作副本中持续工作，本套文档提交后先取得最新文档再比对已有模型。若需要变更命名，维护“逻辑名→实际模型／接口”的映射。新增功能按 F 编号归类，测试按 AC 编号和 DB 编号归类，确保文档与代码能够互相找到。

## 2. API 通用契约

- 示例前缀 `/api/v1`；资源 ID 不可作为授权证明。请求只接受白名单字段，禁止通过通用 PATCH 修改组织、审批人、自定义角色或任意阶段。
- GET 列表返回 `{items, total, page, page_size}`；page 从 1 起，page_size 默认 20、上限 100；排序字段白名单并增加 id 稳定排序。全量导出使用 F42，不用无限分页参数。
- 业务根对象返回 `id, row_version, allowed_actions` 与安全摘要。前端据 allowed_actions 展示按钮，服务端每次动作重新授权，不信客户端回传的动作列表。
- 写操作携带 `expected_version`；版本不符返回 409，返回允许查看的最新版本和中文提示。创建／发送／确认／批量动作使用 `Idempotency-Key`，唯一范围包含组织、操作者、动作和业务对象；同键同载荷返回原结果，同键不同载荷返回冲突。
- 使用有界操作记录或业务表 request_key 实现幂等，不要求先做通用网关。决定类结果保留期间始终可查；临时技术请求记录的过期不能使重复业务动作再次生效。
- 同步创建通常 201，读取／动作结果 200；异步接收 202＋`operation_id, status_url`，202 不是业务成功。400 字段错误，401 未登录，403 明确的功能无权，404 用于隐藏不可见对象，409 状态／版本冲突，413 文件过大，429 频率限制，503 暂不可用。
- 错误结构统一 `{code, message, field_errors, request_id, retryable}`；message 中文，不含原始令牌、外部密钥、无权对象详情或堆栈。网络未知与业务明确失败分开。
- 金额用字符串定点数＋币种＋周期，日期 YYYY-MM-DD，时间带偏移的 ISO 8601；枚举传固定代码，UI 使用中文映射。未知为 null，不把 undefined 输出成文案。
- 附件先检查类型、大小和所属业务，再保存；下载接口校验当前对象／字段权限并签短期受限访问。敏感数据响应不被共享缓存，退出／切组织清理客户端缓存。

DRF 对象权限不会自动把列表逐条过滤，也不能替代创建关联对象的检查；queryset、创建和业务动作均需落实范围校验。参见 [DRF 官方权限说明](https://www.django-rest-framework.org/api-guide/permissions/)。

## 4. 关键请求与返回示例

F06 当前实际接口：GET／POST `/jobs/:id/clarifications/` 分页读取或提问，POST `/jobs/:id/clarifications/:question_id/answer/` 回答；统一 `/api/v1/` 前缀及已有 version 契约。request_key 防止提问重试重复，答案原样重试不新增结果。替换草稿／关闭职位时撤回 pending 问题，已回答历史不变；回答结束本人待办、生成 HR 整理待办，不执行审批。字段、错误与边界见 [后端接口说明](../../apps/api/README.md)；本表其他路径仍为后续逻辑契约。

示例 ID、姓名和日期为虚构。实际传 UUID，以下短 ID 仅帮助阅读；字段变化时同时更新前端、Flutter、接口契约和测试。

### 4.1 人工通过复核

```json
{
  "expected_version": 4,
  "action": "advance",
  "evaluation_id": "evaluation-example",
  "note": "先在一面核实直接带队经历"
}
```

成功：`application.stage=ready_to_schedule`，`row_version=5`，返回 `next_task.id`、`next_task.assignee`，message 为“已通过复核，等待安排面试”。不返回虚假的 `interview.confirmed=true`。如果先被他人处理，409 保留本地备注并提供最新结果。

### 4.2 业务同意下一轮

请求含 `expected_version, action=next_round, comment`；后端锁定 DecisionRequest 与 Application，检查指定人、版本和未结束状态，写决定／阶段事件／待办／外发记录后提交。返回：

```json
{
  "decision": {"status": "decided", "result": "next_round", "row_version": 3},
  "application": {"stage": "ready_to_schedule", "row_version": 9},
  "next_task": {"type": "schedule_interview", "status": "open"},
  "delivery": {"status": "queued"},
  "message": "已同意下一轮，等待 HR 安排"
}
```

### 4.3 批量动作

请求是显式对象列表，每项带 `application_id, expected_version`；建议初始每批不超过 100 条（实施上限，可调），前端展示涉及去重人数。响应是逐项 `succeeded/already_done/failed/conflict` 和原因；不只返回一个 `success=true`。批次可部分成功，每个对象自身事务完整；单项重试沿用相同动作身份防止重复推进。

## 5. 状态机和允许动作

### 5.1 职位与画像

| 对象／当前状态 | 动作→新状态 | 前置与副作用 |
|---|---|---|
| Job draft | activate→recruiting | 有已确认画像、有效负责人；必要审批结果满足当前规则，外部发布另验渠道 |
| Job recruiting | pause→paused；close→closed | 有经办权限，展示在途应聘／外部发布影响；生成同步任务，不自动声称外部完成 |
| Job paused | resume→recruiting；close→closed | 重查画像、负责人和审批有效性 |
| Job closed | reopen→draft | 🔶实施基线：说明原因，重新检查画像／审批后再 activate；保留原关闭历史 |
| Profile draft | submit→in_review | 必要项完整、确认人有效、提交冻结本版本 |
| Profile in_review | approve→confirmed；return/reject→rejected | 指定审批人；退回后复制为新草稿继续，不改正在被审的材料 |
| Profile confirmed | supersede→superseded | 新版确认后切 active_profile；旧版本保留，不迁改旧评估 |

草稿画像审批通过属于岗位要求确认；HC 是否需要审批由明确业务规则决定。未配置时可以本地验证建岗确认链路，但不能显示“编制审批已通过”或未经授权对外发布。

### 5.2 应聘与业务决定

| 当前阶段 | 动作→阶段 | 说明 |
|---|---|---|
| pending_review 待复核 | need_info→needs_information | 记录缺口、跟进人和期限 |
| pending_review／needs_information | advance→ready_to_schedule | HR 复核记录＋安排待办 |
| needs_information | supplement→pending_review | 新材料入本次应聘，可新增评估，不覆盖旧版 |
| ready_to_schedule | schedule→interviewing | 创建本轮排期；应聘进入面试中不等于人员已确认 |
| interviewing | submit_recommendation→pending_decision | 依据已提交反馈，创建业务确认 |
| pending_decision | next_round→ready_to_schedule | 完成原决策并创建新轮次排期待办 |
| pending_decision | contact/assessment→needs_followup | 明确跟进人；测评未接通也只是待办 |
| pending_decision | defer→on_hold | 原决定记录暂缓，必填复查日期；到期生成复查，不自动同意 |
| needs_followup／on_hold | resubmit→pending_decision | 记录新证据／复查原因，新 DecisionRequest，不改旧决定 |
| 可处理的未终结阶段 | reject/withdraw/job_cancelled→closed | 记录结束原因和 closed_at，取消无效后续待办；外部取消需真实结果 |
| pending_decision（P1） | approve_offer→offer_pending | 只是允许准备提案，仍需 Offer 审批 |
| offer_pending（P1） | offer_accepted→onboarding | 接受当前有效已批准／已发送版本，创建入职交接 |
| onboarding（P1） | confirmed_joined→hired；abandon→closed | 已实际入职才 hired；终态必须 closed_at，入职记录单独保留 |

P0 对业务“认可录用方向”可记录决定，但没有 P1 Offer 能力时不得显示“已发 Offer／待入职／已入职”。已结束后再次应聘创建新 Application；纠正误操作走有审计的修正流程，不能随意 PATCH reopened。

### 5.3 面试与反馈

`unscheduled → pending_confirmation → confirmed → completed`；有效场次可取消为 `cancelled`。是否 confirmed 由当前版本所有必需参与人的响应计算；拒绝／改期请求保持待处理，不假设候选人将出席。改期创建新 InterviewRevision 并回 pending_confirmation；旧响应保留但不计入新版。正式取消后重约可建新 Interview 关联同一应聘和轮次。

Feedback 的 `draft → submitted` 独立；有权限修订时生成新 revision，旧 submitted 继续可追踪。完成面试不会自动提交反馈；提交反馈也不自动发推荐卡。过期未到场与正常完成需用结果原因区分，不能因日历时间已过就认定已面试。

### 5.4 Offer 与入职（P1）

`draft → in_approval → approved → sent → accepted/declined/expired`；withdrawn 保留原因。修改已审内容新建版本并回审批；无关备注不能篡改已审条款。Offer 接受、入职日期到来、实际到岗、EHR 同步成功是四件事，分别保存。发送未知状态先核对供应商，不盲目重发新 Offer。

## 6. 关键事务与外部回调

| 流程 | 同一数据库事务内 | 提交后执行 |
|---|---|---|
| 画像确认 | 审批步骤结果、请求结果、画像状态／指针、待办、审计、通知 outbox | 通知 HR／更新卡片 |
| 人工复核 | ReviewDecision、Application、StageEvent、旧待办结束、新待办、审计 | 后续评估／通知 |
| 排期／改期 | 人员锁、冲突检查、新版本、参与人／响应初始化、旧版本失效、旧提醒取消、新待办 | 会议创建／邀请／日历同步；失败显示待处理 |
| 业务确认 | 验证操作者与事项版本、DecisionRequest、应聘状态、任务、审计、outbox | 卡片结果更新和通知 |
| Offer 接受 | 当前版本／身份／期限检查、唯一回复、Offer 状态、OnboardingCase、待办 | 通知 HR 和资料清单 |

回调顺序：验证签名／来源与时效→连接绑定真实组织→查事件去重键与摘要→事务内重新校验对象与人→写结果和事件状态→提交→返回提供方所需响应。旧事件／未知对象不能创建随机新应聘；重复请求得到当前事实。第三方重试、worker 崩溃和网络超时按“至少可能重投”设计，不声称网络端到端天然恰好一次。

worker 执行前重查停用、取消、退订和版本；用租约／行锁领取任务，崩溃后可恢复；失败次数有上限。模型、渠道故障不阻止用户读取已有材料与人工工作。不得向 LLM 发送当前角色无权查看的其他应聘历史。

## 7. 分数、计数和报表口径

**AI 分数为实施建议，需试点校准。** 首版同时返回“分数＋依据覆盖率＋必须项缺口”。各画像规则固定权重和评分标尺；只对有依据可评价项计算加权匹配分，未知项不给伪造负分，并单独降低覆盖率；无可评价项 total_score 为 NULL。支持／不符合不能任意换算成未定义数值，评分标尺、权重和舍入方法必须在确认画像的 scoring_schema_version 中固定并显示。排除信号进入人工复核，不隐式减分到自动淘汰。覆盖不足不排序成高可信推荐；具体推荐阈值待同岗试点确定。不比较不同职位／画像版本的裸分。

| 指标 | 计数与时间依据 | 避免混淆 |
|---|---|---|
| 人才数 | 权限内去重 Candidate；创建时间仅用于“新增人才” | 新投一个职位不是新的人 |
| 新增应聘数 | Application.opened_at 在区间内 | 一人两岗是两条应聘 |
| 当前阶段人数／记录 | 当前 stage 的应聘记录；另提供去重人数字段 | 这是存量，不称历史转化率 |
| 到面场次 | 已明确 completed 且实际完成时间在区间内的 Interview | 预约、取消和未到不算完成 |
| 首次到面人数 | 区间内实际到面的不同 Candidate | 与场次／不同 Application 数分别输出 |
| 首推通过率 | 同一首推 cohort 中获明确业务正向决定的请求数／该 cohort 已作明确决定数 | 待处理、暂缓单列；样本窗和分母显示，不能只拿当前阶段算 |
| 面评逾期 | 已完成且反馈截止已过，当前指定面试官反馈未提交 | 一场多人可有多个待反馈，场次数另报 |
| 招聘周期 | 已入职应聘从 opened_at 到实际入职时间的分布 | 未结束的年龄单列，不能当已完成周期 |
| 渠道转化 | 按应聘来源归因，阶段事件计算指定 cohort 的到达情况 | 多触点归因尚未定义时用首次来源并标口径，不虚构贡献 |

自然日、自然周、自然月按展示时区换算成 UTC 半开区间 `[start,end)` 查询；不同图表共享同一指标定义与权限过滤。P0 只实现已有事实支持的基本计数，后续指标随数据和分期上线。

## 10. 变更与追踪规则

新增／改动功能必须保留 F 编号，补全 04 权限、05 UI 行为、06 数据约束、07 接口与验收中受影响的部分。已有实现与规格不一致时先判断是否影响业务结果：等价命名更新映射；字段／状态语义变化先说明差异；业务待定引用 Q 编号。不要以“用户没懂技术”作为静默改变产品行为的理由。
