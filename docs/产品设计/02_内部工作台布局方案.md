# 内部招聘工作台：页面布局与操作路径

日期：2026-09-22，2026-09-23 更新。状态：产品布局建议稿；后台视觉参考与分端技术架构已确认，具体业务范围仍需按功能逐项定稿。本稿不表示相关页面已经实现。

产品目标：HR 打开就知道先处理什么；查看一个人时能看懂依据、当前进度和下一步责任人；业务负责人和面试官只处理与自己有关的事项。

本轮按企业内部招聘协作设计，桌面端为 HR 主工作区。候选人使用独立的手机任务页。沿用 ToC 的易懂、少填、少跳转原则，保留招聘判断需要的信息密度。当前 `apps/web` 是外部介绍页与虚构简历演示，尚未接入登录或招聘业务后台；本稿描述的是下一阶段内部系统。

## 0. 已确认的外观与技术实现

用户已确认 HR 电脑招聘后台采用 [WorkBuddy 招聘 Demo](https://074efb1a0a9a4e1bbed2ef252b925e87.app.workbuddy.link/) 的外观方向。本地稳定参考保存在 `需求方资料/03_网站调研/2026-09-22_布局复核/`，其中《复核结论》和 HR 首页、职位、候选人列表、候选人详情截图作为开发对照。

采用的视觉特征：深色左侧导航、浅色内容工作区、蓝色主要操作、清楚的页面标题、克制的统计卡片与数据表格，以及列表旁的右侧快速详情。正式页面借鉴整体质感与信息层级，不复制原型代码、演示数据、占位页面或未完成按钮。

颜色与品牌风格沿用现有“知遇 AI”首页，不照搬 WorkBuddy 的独立配色。后台优先复用首页当前设计变量：页面浅蓝灰 `#f7f9fe`、正文深蓝灰 `#24334d`、主蓝 `#2456b8`、浅蓝强调面 `#eaf1fd`、白色卡片和淡蓝灰边框 `#dce4f1`。左侧导航可以使用主蓝的深色层级形成工作台结构，但图标、按钮、选中状态、链接和焦点反馈仍与首页保持同一蓝色品牌语言。警告、失败、待确认等状态保留独立语义色，不能全部染成品牌蓝。

实现分工已经确定：

| 产品端 | 技术方案 | 主要用途 |
|---|---|---|
| HR 电脑招聘后台与外部网页 | React、TypeScript、Tailwind CSS、shadcn/ui、Semi Design | 信息密集工作台、表格筛选、详情抽屉、日程与管理页面 |
| 候选人手机应用与后续 HR 手机应用 | Flutter | 面试确认、改期、进度查看、提醒和移动轻操作 |
| 业务后端与数据接口 | Django、Django REST Framework | 业务规则、权限、状态流转、第三方集成及共享 API |

外观参考不改变本稿的任务结构：首页先显示需要处理的事，一级导航聚焦今天、职位、候选人和面试，AI 放回当前业务上下文，候选人主档案与应聘记录分开。原型中已经发现的筛选未生效、勾选误开详情、`undefined`、占位 AI、虚假邀约结果和角色范围混乱不能进入正式实现。

## 1. 页面从工作流程长出来

| 完成一件事 | 具体步骤 | 主要页面 | 交给谁继续 |
|---|---|---|---|
| 说清要招谁 | 整理需求、补齐要求、确认画像、检查渠道并发布 | 职位 | 业务负责人确认要求，HR 发布 |
| 判断要不要进一步了解 | 收到简历、核对重复、查看岗位依据、人工复核 | 今天 → 候选人 | HR 跟进或安排面试 |
| 验证关键能力 | 约时间、确认参与人、准备问题、记录并提交面评 | 面试 | 面试官提交，HR 汇总 |
| 决定如何推进 | 推荐给业务、确认下一步、执行排期或跟进 | 今天的确认事项、飞书卡片、候选人详情 | 显示具体负责人及待办 |
| 留下可复用记录 | 保存依据、原因与历史，另一个职位重新评估 | 候选人 → 人才档案 | 新职位负责人 |

“今天”是任务入口，“职位、候选人、面试”是长期对象入口。同一条任务在首页、职位页和飞书中显示同一处理结果，不产生三份独立待办。

## 2. 一级导航：四个日常入口，按角色补充

```text
今天
职位
候选人
面试

团队进度       ← 招聘主管或获授权负责人

帮助           ← 左侧底部
设置           ← 左侧底部，内容按权限开放
```

| 入口 | 使用者的问题 | 页面内包含 |
|---|---|---|
| 今天 | 现在该做哪件事？ | 需要我处理、等待他人、今日日程、需要接管的任务 |
| 职位 | 这个岗位招得怎么样？ | 招聘进展、人选、招人要求、JD、渠道与协作设置 |
| 候选人 | 这个人适合哪个岗位，现在该怎么处理？ | 当前应聘、人才档案、匹配依据、应聘历史、面评 |
| 面试 | 何时面、谁来面、还有谁没提交反馈？ | 待安排、日程、待确认、待反馈、准备与评价 |
| 团队进度 | 哪些岗位卡住了，需要谁帮助？ | 管辖范围内的进展、滞留事项、负责人和可下钻明细 |
| 设置 | 谁能看、谁能操作、连接是否正常？ | 个人偏好；有权限者管理组织、成员、渠道、飞书与操作记录 |

业务确认在“今天”集中处理，在具体职位/应聘中保留记录；飞书是同一事项的另一入口。首版不另设功能重复的“业务协同中心”。

人才库基础能力放在“候选人”的“人才档案”标签；人才地图、语义检索和再触达随后续阶段加入。AI 画像、AI 评估、AI 提纲分别跟随职位、人选和面试，不要求使用者到独立 AI 菜单中反复选择上下文。

## 3. 页面公共骨架

```text
┌──────────────────────────────────────────────────────────┐
│ 企业/工作范围     当前页面路径    搜索职位与候选人    消息/本人 │
├───────────┬──────────────────────────────────────────────┤
│ 今天       │ 页面标题、当前范围                 当前主要操作 │
│ 职位       │ 标签 / 简单筛选 / 更多筛选                     │
│ 候选人     │                                              │
│ 面试       │                 主要工作区域                  │
│            │                                              │
│ 团队进度   │        详情或日程仅在当前任务需要时出现          │
│            │                                              │
│ 帮助/设置  │ 保存、提交、发送结果在操作附近反馈               │
└───────────┴──────────────────────────────────────────────┘
```

桌面建议左栏约 200–224 像素、顶栏约 56–64 像素，作为原型起点，后续以实际中文内容和可用性测试调整。导航固定位置，主内容自适应。页面标题下明确“我的职位”“当前职位”“本部门”等范围，不让用户猜统计属于谁。

主要动作跟随页面：职位页“新建职位”，应聘页“导入简历”，面试页“安排面试”。顶栏保持搜索、消息与个人入口。跨页搜索也遵守数据权限，不能通过搜索结果或数量泄露不可见的人选。

窄屏先收起导航，再让列表与详情切换；宽屏才展开并排证据。优先保留主内容宽度。操作成功返回原队列时，保留筛选条件和阅读位置。

## 4. “今天”：任务占主位，日程占辅位

HR 首页建议约三分之二为任务，三分之一为今日日程；如果窗口不足，日程排到任务之后。没有长期常驻的第三个 AI 聊天栏。

第一层显示“需要我处理”及待复核、待安排、待我提交的面评、待我确认的事项数量。点击数量进入对应队列，数字必须能找到组成它的事项。

第二层是可直接行动的列表。每行只保留：**对象与职位、为什么现在处理、期限、一个主要动作**。例如“渠道经理｜候选人甲缺少带队经历依据｜开始复核”。内部示例均为虚构。

第三层把“等待他人”单独放置：等待谁、等了多久、上次提醒何时发送。HR 不承担的业务决定不能算成“需要我确认”；具备权限时才出现提醒入口。

右侧今日日程显示时间、职位、面试轮次、参与人确认状态及“准备面试”。“已安排”“已发邀请”“对方已确认”明确分开。

解析或发送异常出现时，展示具体对象、影响和重试/交给管理员入口；正常任务保持低干扰。任务优先级先按已超期、近期到期、其余排序，排序依据可见；不使用不明来源的“AI 紧急指数”。

首次使用没有职位时显示“创建第一个职位”；没有创建权限则显示联系负责人或请求分配。已完成所有待办时给出完成状态和下一场面试，不能把空页面误当加载失败。

## 5. 职位：一个岗位的一切围绕它展开

职位列表默认呈现我负责或协作的有效职位。建议字段为职位名称、部门/地点、负责人、计划人数、当前进展、需处理事项。状态使用清楚的中文，草稿、招聘中、暂停、关闭分别筛选。

点击职位进入完整页面，顶部持续显示职位名、状态、计划人数与责任人。页内采用四个标签：

1. **招聘进展**：各阶段数量、卡住的事项和下一步负责人；点击人数能下钻。
2. **候选人**：只显示这个职位的应聘记录，与全局“候选人”使用同一套列表和详情。
3. **招人要求**：对外 JD、内部画像分别展示；规则分为必须满足、优先考虑、排除信号，每项另标已确认或待确认。排除信号须说明与岗位的关系及证据，待确认条件不能直接用于淘汰。AI 生成后仍是草稿。
4. **渠道与协作**：发布渠道及独立状态、岗位成员、业务负责人、审批和通知配置。

新建使用“填写基本需求 → 确认招人要求 → 检查并发布”。用人需求和编制审批放在职位上下文中；独立 HC 管理是否必要，需结合真实审批频率再决定，不将供应商手册全部菜单直接搬入首版。

画像变更显示版本差异、确认人及受影响评估；旧判断保持当时依据。频道/渠道发布部分失败时保留成功结果，允许重试失败部分。

## 6. 候选人：最重要的是看懂依据后能做决定

全局候选人页有两个标签：**当前应聘、人才档案**。

- 当前应聘一行代表“某个人应聘某个职位的一次记录”。同一人申请两个职位可有两行，列表明确标注职位；数量称“应聘记录”，不能误称不同人数。
- 人才档案按人去重；查看当前与历史应聘时，只显示有权限访问的内容。重新用于新职位时创建新的应聘记录，保留原记录。
- 搜索与常用筛选放在顶部：姓名/关键词、职位、阶段、负责人。来源、时间等放入更多筛选，支持恢复上次使用条件。

复核时宽屏建议采用“左侧简短队列 + 中间当前人选 + 按需打开的原文证据”。中间第一屏按以下次序布局：

1. 姓名、当前应聘职位、本次阶段、HR 负责人。
2. 简短的 AI 建议和待核实项，材料不足与明确不满足分开。
3. 岗位要求 → 判断 → 对应证据；点击来源定位原简历或已确认面评。
4. 当前可用的下一步，例如安排面试、记录核实结果、暂不推进。

原简历、面试评价、应聘历史、操作记录放在详情标签中。匹配总分按原 D1 保留在可展开的评估区域，同时显示职位和画像版本；不把不同职位的分数做统一能力排名。

批量操作从勾选开始才出现，执行前分别说明应聘记录数、去重人数、涉及职位及影响。例如“2 条应聘记录，涉及 1 人、2 个职位”，动作逐条作用于选中的本次应聘。勾选不能触发打开详情。推进、暂不推进和人才复用都记录本次应聘及原因，不删除个人档案。

常见阅读可使用侧边详情快速完成；需要比较证据、编辑评价或处理多轮历史时展开成完整页面。避免抽屉内再开抽屉。普通屏幕采用列表与详情两步切换，不能为了三栏把简历压得难读。

## 7. 面试：排期、准备、反馈连在一起

面试入口默认呈现“日程”，旁边提供待安排、待确认、待反馈三个队列。HR 可以管理相关岗位；面试官只看到自己被安排的场次与反馈。

排期页突出本次职位与轮次，选择参与人、时间及时区、地点/会议方式，预览通知后发送。时间冲突、取消或改期给出明确结果。

准备页建议左侧看简历与本轮需验证能力，右侧是可编辑的问题提纲；面后切换到结构化反馈：已验证能力、事实依据、疑问、下一步建议。草稿自动保存状态与最终“提交面评”分开。

日程状态与面评状态并列显示：一场面试可以已经结束，但评价尚未提交。AI 生成内容始终先作为草稿，只有面试官提交后才是确认后的评价。转写、纪要、录音分析按后续阶段建设，手工面评在首版即可完成。

## 8. 同一套数据，不同角色看到不同工作区

| 角色 | 默认打开 | 核心内容 | 受限或简化的内容 |
|---|---|---|---|
| HR | 今天 | 复核、排期、跟进、相关岗位及人才 | 仅授权岗位/字段；团队全局数据按权限开放 |
| 面试官 | 我的面试 | 今日场次、面试准备、待提交面评 | 不展示全公司候选人、无关面评、薪资或批量导出 |
| 用人负责人 | 待我确认；飞书可直达同一事项 | 招人要求、推荐人选、本部门进展 | 默认精简页面，不要求学习完整 HR 操作区 |
| 招聘主管 | 团队进度 | 岗位瓶颈、事项负责人、待协助任务 | 按所管组织和授权范围展示 |
| 管理员 | 设置 | 成员授权、连接状态、异常与操作记录 | 管理配置不自动授予全部招聘材料读取权限 |

兼任多个职责的人可以切换工作视图，但只切换到已获授权的角色与范围；前端切换不能产生新权限。候选人使用独立本人任务页，不进入内部菜单，也不看到内部评分和其他人的材料。

团队进度的首版以可下钻的阶段数量、待办及负责人为主。完整漏斗、效率分析、对话报表和周报需要统一指标口径，按后续阶段加入。主管视角不能只做漂亮数字而找不到具体卡点。

## 9. AI 和通知怎么放

页面内 AI 入口围绕当前工作：职位中“生成招人要求”，应聘中“查看匹配依据”，面试中“准备问题”。上下文自动带入并可核对，不让用户重新输入职位和人名。

全局帮助可以逐步扩展为对话助手，当前页面业务操作始终有清楚的按钮和表单。AI 需要有权限的人确认的动作、会发送给别人的内容，都先展示对象、依据与影响。

消息列表负责提醒与回到原事项，首页负责行动。已发送、等待回执、对方已确认分别展示；飞书重复操作、卡片过期、他人已处理时返回最新结果。业务负责人同意二面，仅代表产生排期待办，不能立即显示已约好。

## 10. 首版与后续布局边界

| 首版必须走通的链路 | 后续逐步展开 |
|---|---|
| 职位、JD、画像、必要审批和业务澄清 | 画像更新建议与样本学习 |
| 至少一个真实渠道发布与回传、邮箱入库、解析去重 | 主动寻访、更多渠道自动化 |
| 当前应聘、人才主档案、依据评估和人工复核 | 语义搜索、人才地图、同岗召回 |
| 基础多轮约面、参与人确认、提醒、提纲、手工面评 | 录音转写、AI 纪要与档案补全 |
| 飞书推荐、决定回写及可追踪下一步待办 | 测评、背调、Offer 审批发送和入职对接 |
| 数据范围、失败恢复和基本团队进度 | 完整经营报表、对话分析和周报 |

完整录用流程属于长期产品结构；Offer 全链路按现有 v3 表述在后续阶段，是否提前需单独定范围。不要在首版菜单里堆放只能显示“敬请期待”的页面。各阶段的具体字段、状态与权限需在该功能开发前细化。

## 11. 评审时用真实任务检查布局

以下为计划执行的体验验证，尚未实测，不承诺已有改善比例或具体耗时。

1. 新 HR 打开首页，能指出第一件要处理的事，以及等待他人的事项。
2. 从职位找到待复核人选，查看证据后安排一次面试，返回时保留列表位置。
3. 同一个人有两个职位的应聘，用户能分辨本次操作影响哪个职位。
4. 业务负责人在飞书同意下一轮，HR 页面出现对应待办，而不是虚假的预约成功。
5. 面试官完成一场面试后保存草稿，再提交反馈，能清楚区分两个状态。
6. 渠道失败或评估失败，仍可找到已成功入库的材料并继续人工处理。
7. 面试官、业务负责人、主管分别检查菜单、搜索、数量、详情与导出范围。
8. 小屏和键盘操作能完成相同主要任务，详情关闭后焦点回到原位置。

本轮先评审入口是否易懂、首页是否能行动、候选人是否便于判断。视觉细节在结构确定后再定；账号切换、按钮与示例数量用于布局讨论，不代表正式权限或后台处理已实现。
